一、数据库范式

1. 第一范式（1NF）
要求：每个字段都是不可再分的原子值，不能在一个字段中存多个值。
反例：一个字段存"张三,李四,王五"。
正例：拆成多行，每行存一个人名。

2. 第二范式（2NF）
要求：在1NF基础上，消除部分依赖，非主键列必须完全依赖于整个主键（针对联合主键）。
反例：订单明细表用(订单号,产品号)做主键，表里却只存了产品名称（只依赖产品号，不依赖订单号）。
正例：把产品名称拆到产品表中，订单明细表只存产品号。

3. 第三范式（3NF）
要求：在2NF基础上，消除传递依赖，非主键列不能依赖于其他非主键列。
反例：学生表中存了院系名和院系地址，院系地址依赖院系名，院系名依赖学号，存在传递依赖。
正例：把院系信息拆到院系表中，学生表只存院系号。

4. 范式与反范式
范式化优点：减少数据冗余、更新异常少、存储紧凑。
范式化缺点：多表JOIN多，查询性能差。
反范式：适当冗余字段，减少JOIN，用空间换时间，适合读多写少的业务。
实际项目通常在3NF基础上做适度反范式。

二、事务隔离级别

1. 并发事务问题
脏读：一个事务读取到另一个事务未提交的修改。
不可重复读：同一事务内，两次读取同一行数据结果不同（被其他事务UPDATE提交）。
幻读：同一事务内，两次查询的行数不同（被其他事务INSERT/DELETE提交）。

2. 四种隔离级别
读未提交（READ UNCOMMITTED）：最低隔离级别，什么问题都可能发生。
读已提交（READ COMMITTED, RC）：解决脏读，可能有不可重复读和幻读。
可重复读（REPEATABLE READ, RR）：MySQL默认级别，解决脏读和不可重复读，InnoDB通过MVCC+间隙锁解决幻读。
串行化（SERIALIZABLE）：最高隔离级别，所有事务串行执行，性能最差。

3. 查看与设置隔离级别
查看：SELECT @@tx_isolation;
设置（全局）：SET GLOBAL tx_isolation = 'READ-COMMITTED';
设置（当前会话）：SET SESSION tx_isolation = 'READ-COMMITTED';

三、MVCC 多版本并发控制

1. MVCC概念
MVCC（Multi-Version Concurrency Control）通过保存数据的多个版本，实现读不阻塞写、写不阻塞读，提升并发性能。
InnoDB在RR隔离级别下通过MVCC实现可重复读。

2. MVCC实现原理
隐藏字段：每行数据有两个隐藏列——trx_id（最近修改该行列的事务ID）、roll_pointer（指向undo log中的旧版本）。
Undo Log回滚日志：记录数据修改前的旧版本，形成版本链。
Read View读视图：事务启动时生成，记录当前活跃的事务ID列表，用来判断哪个版本对当前事务可见。

3. 可见性判断规则
遍历版本链，比较版本的trx_id与Read View：
如果trx_id < Read View最小活跃事务ID，说明该版本在事务启动前已提交，可见。
如果trx_id >= Read View最大活跃事务ID，说明该版本在事务启动后才开启，不可见。
如果trx_id在活跃列表中，说明该版本还未提交，不可见。
否则可见。

四、锁机制

1. 锁的分类
按粒度分：表级锁（MyISAM）、行级锁（InnoDB）、页级锁。
按性质分：共享锁（S锁，读锁）、排他锁（X锁，写锁）。
按状态分：意向共享锁（IS）、意向排他锁（IX），加表锁前先检查意向锁。

2. 行锁类型
记录锁（Record Lock）：锁定单行记录。
间隙锁（Gap Lock）：锁定索引记录之间的间隙，防止幻读。
临键锁（Next-Key Lock）：记录锁+间隙锁，左开右闭区间，InnoDB默认行锁算法。

3. 行锁加锁时机
InnoDB的行锁是加在索引上的。如果查询没有用到索引，会退化为表锁。
UPDATE/DELETE/INSERT自动加排他锁。
手动加共享锁：SELECT ... LOCK IN SHARE MODE;
手动加排他锁：SELECT ... FOR UPDATE;

4. 死锁
两个事务互相持有对方需要的锁，互相等待，导致死锁。
InnoDB有死锁检测机制，会自动回滚代价较小的事务。
避免死锁：按固定顺序访问表和行、大事务拆小、降低隔离级别、为查询加合适索引。

五、B+树索引原理

1. B树与B+树对比
B树：每个节点都存数据和指针，叶子节点不相连。
B+树：只有叶子节点存数据，非叶子节点只存索引键；叶子节点用双向链表相连。
MySQL用B+树的原因：
（1）非叶子节点不存数据，一个页能存更多索引键，树更矮，IO次数少。
（2）叶子节点链表相连，范围查询效率高。
（3）查询性能稳定，每次都要查到叶子节点。

2. 索引页
InnoDB以页（16KB）为单位读写数据，一棵B+树一般3-4层就能存储千万级数据。
千万级表查询一次最多3-4次磁盘IO。

3. 索引失效场景
（1）对索引列使用函数或运算：WHERE YEAR(create_time) = 2024。
（2）隐式类型转换：WHERE phone = 13800138000（phone是字符串）。
（3）LIKE以%开头：WHERE name LIKE '%张三'。
（4）联合索引不满足最左前缀。
（5）OR两边有一边没索引。
（6）使用 != 或 <> 可能导致索引失效。
（7）NOT IN、NOT EXISTS可能失效。

六、SQL 查询优化

1. EXPLAIN执行计划
使用：EXPLAIN SELECT ...;
重点关注列：
id：查询序号，越大越先执行。
select_type：查询类型，SIMPLE简单查询、PRIMARY外层查询、SUBQUERY子查询。
table：访问的表。
type：访问类型，性能从好到差：system > const > eq_ref > ref > range > index > ALL。
possible_keys：可能用到的索引。
key：实际用到的索引。
rows：预估扫描行数。
Extra：额外信息，Using index表示覆盖索引，Using filesort表示文件排序，Using temporary表示临时表。

2. 常见优化手段
（1）SELECT具体列，不用SELECT *。
（2）建合适的索引，覆盖索引避免回表。
（3）大分页用延迟关联：先查主键再关联原表。
示例：SELECT * FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t ON o.id = t.id;
（4）深分页优化：WHERE id > 上次最大id LIMIT 10。
（5）避免在索引列上做函数运算。
（6）小表驱动大表。
（7）批量插入用批量VALUES代替单条INSERT。

3. COUNT优化
COUNT(*)：统计所有行，包括NULL行，InnoDB会选择最小索引遍历。
COUNT(1)：与COUNT(*)性能基本一致。
COUNT(列名)：不统计该列为NULL的行。
MyISAM的COUNT(*)很快（有计数器），InnoDB需要逐行统计。
大表COUNT优化：用Redis维护计数，或预估行数用SHOW TABLE STATUS。

七、日志体系

1. Redo Log（重做日志）
作用：保证事务持久性（Durability），记录数据页的物理修改。
特点：InnoDB引擎层日志，循环写入，大小固定，先写日志再写磁盘（WAL机制）。
崩溃恢复：MySQL重启时重做已提交但还没刷盘的修改。

2. Undo Log（回滚日志）
作用：保证事务原子性，记录数据修改前的旧版本。
特点：用于事务回滚和MVCC快照读。
事务提交后undo log不是立即删除，要等到没有事务引用该版本。

3. Bin Log（归档日志）
作用：记录所有DDL和DML语句，用于主从复制和数据恢复。
特点：MySQL Server层日志，追加写入，不循环。
三种格式：STATEMENT（记录SQL）、ROW（记录行变更）、MIXED（混合）。

4. 两阶段提交
Redo Log和Bin Log的提交分为两个阶段：
Prepare阶段：写Redo Log并标记为Prepare。
Commit阶段：写Bin Log，然后提交Redo Log。
保证Redo Log和Bin Log的数据一致。

八、主从复制

1. 复制原理
主库写Bin Log。
从库IO线程拉取主库Bin Log，写入Relay Log（中继日志）。
从库SQL线程读取Relay Log，重放SQL，实现数据同步。

2. 复制方式
异步复制（默认）：主库写完Bin Log就返回，不等从库确认，可能丢数据。
半同步复制：主库至少等待一个从库收到Bin Log才返回。
全同步复制：主库等待所有从库执行完才返回，性能差。

3. 主从延迟
原因：单线程重放（5.6之前）、大事务、从库性能差、网络延迟。
解决：开启并行复制（5.7基于组提交）、拆分大事务、提升从库配置、读走主库或加缓存。
